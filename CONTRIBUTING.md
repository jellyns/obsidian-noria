# Contributing

Thanks for contributing to Noria. Noria is an Obsidian desktop plugin that reads and writes local Markdown files and Obsidian plugin settings, so contributions should protect existing vault content first.

## Before You Start

1. Open an issue first, or explain the target clearly in the PR description: bug fix, documentation, feature, refactor, or release work.
2. Keep changes focused. Do not mix unrelated formatting or opportunistic refactors into feature or bugfix work.
3. Do not commit local plugin settings, test vaults, `node_modules/`, or private planning files.
4. If a change writes to a user vault, describe the path, trigger, and overwrite behavior.

## Local Development

```bash
npm install
npm run build
npm test
```

To install the release build into a separate test vault:

```bash
npm run install:vault -- F:/NoriaTest
```

The install script copies only `manifest.json`, `main.js`, and `styles.css` into the target vault's `.obsidian/plugins/noria/` directory and preserves any existing `data.json`.

## Documentation

Update documentation whenever user-visible behavior changes:

- `README.md`: plugin positioning, core workflows, installation, first run, screenshots, and project overview.
- `docs/USER-GUIDE.md`: Home dashboard, Task Board, Task Timeline, Review Center, Data API, export, migration, and common settings.
- `docs/FAQ.md`: troubleshooting, confusing states, and legacy migration notes.
- `docs/SETTINGS-MAPPING.md`: Settings UI, `data.json`, runtime bridge, Data API, Home widgets, review evidence, and managed path changes.
- `README.zh-CN.md` and `docs/zh-CN/`: Chinese mirror docs. Keep them aligned when the default English docs change.
- `CHANGELOG.md`: next-version user-visible changes.

Public docs should not link to private local planning files. Keep English screenshots in `docs/assets/en/` and Simplified Chinese screenshots in `docs/assets/zh-CN/`; use matching filenames and image order in each README and User Guide pair.

## PR Checklist

PR descriptions should cover:

- Background: why the change is needed.
- Scope: affected views, commands, settings, files, and generated assets.
- User impact: what existing users need to know.
- Verification: commands run and manual Obsidian checks performed.

Before requesting review, run:

```bash
npm run check
git diff --check
```

If a check cannot be run, state that clearly in the PR.

## Release Assets

A normal user installation should contain only:

- `manifest.json`
- `main.js`
- `styles.css`
- `data.json` generated by Obsidian after settings are saved

Do not instruct users to clone the source repository into `.obsidian/plugins/noria/`.

`main.js` and `src/generated/embedded-runtime-sources.js` are pure build outputs and are not part of the source-branch contract. `styles.css` remains tracked because it also contains authored plugin CSS. The tag workflow rebuilds and validates the final assets before attaching them to the release.

## Publishing A Release

1. Update `minAppVersion` in `manifest.json` when compatibility changes.
2. Run `npm version patch`, `npm version minor`, or `npm version major`. The version lifecycle synchronizes `manifest.json` and `versions.json`.
3. Run `npm run check` and `npm run release:check`.
4. Push the generated version commit and its exact numeric tag. Do not prefix the tag with `v`.
5. The release workflow builds again, verifies the tag against `manifest.json`, attests the build, and creates a draft GitHub release containing `manifest.json`, `main.js`, and `styles.css`.
6. Inspect the draft assets and release notes before publishing.

The root `manifest.json` is used for community-directory metadata. Installed files are downloaded from the GitHub release whose tag exactly matches the manifest version.
